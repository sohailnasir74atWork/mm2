# MM2 Values — Cost Optimization + Adopt Me Feature Port

Written 2026-09-05. Firebase project `mm2vlaues-ed80c`. **Firebase only — no Supabase.**
Adopt Me (`adoptme-jan7`) is the reference app; every feature below already runs there.

Sibling reports: `adoptme-jan7/COST_OPTIMIZATION_2026-09.md`,
`Blox_Fruit/COST_OPTIMIZATION_2026-09.md`. MM2 was cloned from the same
codebase, so it inherited the same three patterns (per-leaf profile reads,
open rules, no retention) — measured below, not guessed.

## 0. Measured baseline

Cloud Monitoring, 7 days (2026-08-29 → 2026-09-05), plus a live 10-minute
`firebase database:profile` run on 2026-09-05 (22,847 operations recorded).

| Meter | 7-day | ≈ /month | Free tier | ≈ Billed /month |
|---|---:|---:|---|---:|
| RTDB egress | 3.57 GB | 15.4 GB | 10 GB | **$5.40** |
| Firestore reads | 1,726,463 | 7.4 M | 50k/day | **$3.54** |
| Firestore writes | 50,593 | 0.22 M | 20k/day | $0 |
| Cloud Functions invocations | 86,033 | 0.37 M | 2M/mo | $0 |
| RTDB storage | 238 MB | — | 1 GB | $0 |

**Total ≈ $9/month.** That is small, and it is the honest number — MM2 is not
Blox Fruit ($122/mo) or Adopt Me ($51/mo). Two things still make this worth
doing now:

1. **The waste is proportionally worse than either sibling.** 79% of every
   RTDB read in the profile window is one bug (F1). Only 32% of RTDB egress is
   actual payload; the other 68% is per-operation overhead from millions of
   tiny reads.
2. **The security holes are not proportional to the bill.** Firestore is fully
   world-writable (S1) and RTDB `/users` is world-readable with 81,431 email
   addresses and FCM tokens in it (S2). Those cost $0/month right up until
   somebody notices.

Scale markers: **81,431** users, **91,284** public chat messages, **68,323**
private chat threads, **70,730** presence rows against a peak of **160**
concurrent connections, ~1.46 M RTDB reads/day.

## 1. Cost findings

### F1 — `profileCache` does 16 separate RTDB reads per profile — 79% of all database reads
**Severity: high · Effort: one function · Risk: none · Saving ≈ $3.5/mo**

`Code/Helper/profileCache.js:34-42` stubs out every Supabase getter to return
`null` — correct for a Firebase-only app. But `assembleAndCacheProfile` was
written for the Supabase path: when a row comes back `null` it falls back to
reading that field as its **own RTDB leaf**. With all four getters stubbed,
every cache miss reads 3 game/shop leaves plus 13 fallback leaves — 16
round-trips for one profile.

The profiler shows it exactly. These are the top 13 paths by operation count,
each one a leaf of the same record, each fired the same number of times:

| Path | listen ops / 10 min |
|---|---:|
| `users/$id/shop/activeItems` | 747 |
| `users/$id/lastGameWinAt` | 710 |
| `users/$id/$id` (fallback list) | 688 |
| `users/$id/isPro` | 687 |
| `users/$id/hasRecentGameWin` | 684 |
| `users/$id/avatar` | 667 |
| `users/$id/displayName` | 660 |
| `users/$id/admin` | 659 |
| `users/$id/isModerator` | 658 |
| `users/$id/isTrusted` | 658 |
| `users/$id/isCMSR` | 658 |
| `users/$id/isHelper` | 657 |
| `users/$id/topBadge` | 657 |
| **⇒ combined** | **~8,000 of 10,165 total listens (79%)** |

**Fix:** one `get(users/{uid})` per cache miss, then read every field off the
returned object. 16 operations → 1. Raise the cache TTL from 30 minutes to
6 hours; `invalidateFullProfile()` already exists for the cases that must
refresh immediately (role granted, profile edited).

**Effect:** ~1.15 M fewer RTDB reads/day (−79%), and the same drop in the
per-operation overhead that is 68% of the egress bill.

### F2 — five config nodes re-read on every app launch
**Severity: low · Effort: small · Risk: none**

`api`, `free_translation`, `single_offer_wall`, `image_url` are read fresh on
every cold start (`GlobelStats.js:322-343`, `:497`). The profiler counts ~102
listens per 10 minutes for each — one per launch, four launches' worth of
round-trips before the first screen paints. `server` already caches for 3
hours and is the model to copy.

**Fix:** one MMKV-cached read with a 6-hour TTL for all four. Removes ~4 reads
per launch and ~40k reads/day, and makes cold start faster.

---

### F3 — `presence` has 70,730 rows for 160 concurrent users
**Severity: medium · Effort: port one function · Risk: low**

Peak concurrent connections is 160; `/presence` holds 70,730 keys. When an app
is killed without `onDisconnect` firing, the `true` value is left behind
forever. `OnlineUsersList.jsx:200-202` queries
`presence.orderByValue().equalTo(true)` and gets those ghosts back, so the
online list is both wrong and expensive.

**Fix:** port Adopt Me's `clearPresenceNode` — a scheduled function that wipes
the whole node every 20 minutes. Live clients re-arm their own presence within
seconds, so the node self-heals to only genuinely-online users.

---

### F4 — no retention on `chat_new` (91,284 messages) or `private_messages` (68,323 threads)
**Severity: medium · Effort: port three functions · Risk: destructive, needs go-ahead**

MM2 has neither of Adopt Me's retention jobs. Both nodes grow forever. Storage
is 238 MB of the 1 GB free tier today, so this is not yet a bill — it is a
cliff. Public chat also dominates payload egress: `chat_new` is 1.12 MB of the
1.69 MB read in the profile window (66% of all payload bytes) because every
message carries its own avatar URL and item array.

**Fix:** port `cleanupOldPublicChats` (3-day retention), `cleanupGroupChatMessages`
(keep newest 300/group) and `cleanupOldPrivateChats` (20-day retention, with
the resumable cursor Adopt Me added after its version timed out nightly).

**These delete production data. Do not deploy without an explicit go-ahead and
a retention window you have chosen yourself.**

---

### F5 — user search downloads up to 500 full user records
**Severity: medium · Effort: small · Risk: none**

`SocialDashboard.js:319` and `:414` fall back to
`query(ref(db,'users'), orderByChild('displayName'), limitToFirst(500))` and
filter client-side. Each call downloads 500 complete user objects — emails,
FCM tokens, everything — to match a substring. The profiler caught the whole
`users` node being read 9 times for 0.11 MB in ten minutes.

**Fix:** drop the broad scan. The indexed `startAt/endAt` prefix query above it
already covers the real case; a contains-match is not worth 500 records.

## 2. Security findings

### S1 — Firestore is world-readable AND world-writable until 2029
**Severity: critical · Effort: one rules file · Risk: must be staged carefully**

Live ruleset `172c3c69-3d97-44a0-8ca5-c6c6e231ead8`, last touched 2026-03-05:

```
match /{document=**} {
  allow read, write: if request.time < timestamp.date(2029, 3, 5);
}
```

This is the Firebase console's default "test mode" rule with the expiry pushed
out. Anyone who extracts the project ID from the app bundle can read, rewrite
or delete **every** Firestore document — `trades_new`, `reviews`,
`designPosts`, `user_profiles`, `game_scores`, `notifications`. No
authentication required.

**Fix:** a real ruleset. Written to `firestore.rules` in this repo, wired into
`firebase.json`. Not deployed — see §4.

---

### S2 — RTDB `/users` is world-readable and world-writable
**Severity: critical · Effort: rules edit · Risk: breaks old builds if over-tightened**

Verified against production with an unauthenticated request — no token, no
auth:

```
GET https://mm2vlaues-ed80c-default-rtdb.firebaseio.com/users.json?orderBy="$key"&limitToFirst=1
→ {"...":{"avatar":"...","displayName":"...","fcmToken":"...","id":"...",
   "isBlock":false,"isPro":false,"rewardPoints":0, ...}}
```

81,431 records, each with an FCM token (push to any user) and, for accounts
created through email sign-in, an address. The live rules also grant
`"$userId": { ".write": true }`, so any anonymous caller can rewrite any
profile — including setting `admin: true` on themselves.

Every other node is the same: 40 of the 60 nodes in the live ruleset are
`".read": true, ".write": true`.

**Fix:** staged, so old builds keep working (see §4). Stage 1 is
`"auth != null"` on `/users` — blocks anonymous scraping only, every
signed-in read keeps working. Stage 2 write-locks the role flags so a client
cannot promote itself, which is a prerequisite for the whole role system in
§3 meaning anything at all.

> Note: the role gates in §3 are **UI-only** until S2 stage 2 is live. Anyone
> can flip their own `admin` flag with a REST call today, and will still be
> able to after the app-side work ships. The rules are the enforcement.

## 4. Order of work, and what must not be automated

**Backward compatibility rule, applied throughout:** MM2 is in production with
old builds in the field. Server-side changes are additive only. Rules tighten
to `auth != null`, never to `false`, on any node an existing build reads.

1. **App-side, ships in the next build, zero deploy risk:** F1, F2, F5, P1–P5, P12–P15.
2. **New Cloud Functions, additive:** `clearPresenceNode` and the role-roster
   triggers. Safe to deploy — nothing deletes user data.
3. **Retention functions (F4):** destructive. Needs a chosen retention window
   and an explicit go-ahead.
4. **Rules (S1, S2):** the highest-value change and the one most able to break
   a live app. Deploy by hand, watch the logs, keep the previous ruleset ready
   to roll back.

Nothing in categories 3 and 4 has been deployed by this session. The files are
in the repo and the exact commands are in §5 of the handoff notes.

## 6. Trade screen — 2026-09-06

Reported as "search is not working". It never worked. Six defects, found and
fixed.

### T1 — search queried fields that no document has
**Root cause. Search returned zero results for every query, always.**

`Trades.jsx` searched `hasItemNames` and `wantsItemNames` with
`array-contains`. Nothing in the app has ever written those fields. Verified
against production:

```
GET .../documents/trades_new?pageSize=3
fields: avatar, description, flage, hasItems, hasRecentGameWin, hasTotal,
        isFeatured, isPro, lastGameWinAt, rating, ratingCount, robloxUsername,
        robloxUsernameVerified, status, timestamp, traderName, userId,
        wantsItems, wantsTotal
hasItemNames:   ABSENT
wantsItemNames: ABSENT
```

All 53,983 trade documents are missing them.

**Fix.** `Code/Trades/tradeSearchIndex.js` builds the token array, and
`HomeScreen.jsx` writes it on every new trade. Tokens are the lowercase full
item name **plus each individual word**, because `array-contains` matches an
element exactly — storing only full names means "knife" can never find
"Flowerwood Knife". Existing trades need
`scripts/backfill-trade-search-index.js`.

### T2 — the "You" side had no database index
`hasItemNames CONTAINS + timestamp DESC` exists in production. The matching
`wantsItemNames` index does not, so even with T1 fixed, half of every search
would fail. There was no `firestore.indexes.json` in the repo at all.

**Fix.** Generated `firestore.indexes.json` from the 12 live indexes and added
the missing one. Note the Firestore REST API ignores the collection group in
the request path and returns every index in the database; the real collection
comes from each index's resource name. Reading it the obvious way produces a
file that would try to create 192 wrong indexes.

### T3 — one pagination cursor shared by two different queries
`searchLastDoc` was passed as `startAfter` to both the has-side and wants-side
queries. A document's cursor position is only meaningful inside the query that
produced it, so page two was wrong whenever both sides were on. `searchHasMore`
also compared the merged count against the page size, which can be double it.

**Fix.** A cursor per side, and "more pages" means at least one side returned a
full page.

### T4 — search errors were swallowed
Both `catch` blocks logged to the console and continued, so a missing index —
which was actually the case — was indistinguishable from "no trades matched".
This is why T1 and T2 stayed invisible.

**Fix.** A failed-precondition now names the field and tells you to deploy the
index file.

### T5 — both search-side toggles could be switched off
The guard tested the state *before* the toggle:

```js
if (!searchInHas && !searchInWants) setSearchInWants(true);
setSearchInHas(!searchInHas);
```

With Me on and You off, the condition is false, so nothing is corrected and
`setSearchInHas(false)` leaves both off. Every later search was then refused
with "You must select at least one side to search", and no combination of taps
recovered without a restart.

**Fix.** Refuse to switch off the last active side.

### T6 — featured trades used a fake document id
Featured trades were stored as `id: \`featured-${docSnap.id}\``. The delete
handler stripped the prefix; nothing else did.

- **Saving a featured trade silently failed.** It wrote
  `savedTrades/<uid>/featured-<docId>`, and the Saved tab then looked up
  `trades_new/featured-<docId>`, which does not exist. The bookmark icon
  filled in and the trade never appeared in Saved.
- `keyExtractor` produced `featured-featured-<id>`.

**Fix.** Keep the real document id; prefix only inside `keyExtractor`, where
it is just a React key. `fetchSavedTradeRefs` now strips the legacy prefix on
read, so bookmarks saved before this build start working with no migration.

### Also fixed
- Pull-to-refresh during a search ran `fetchInitialTrades` but left
  `isSearchMode` true, so the list filled with unfiltered trades and the next
  scroll-to-end replaced them with search results again.
- `t("feature")` is not a key, so the confirmation button read **"feature"**.
- Two `Alert` titles were hardcoded English in an otherwise translated screen.
- Instant local matching over already-loaded trades. No reads, and it is the
  only path that matches a partial word.

### Commands for the trade fixes

```bash

```

Then backfill the 53,983 existing trades. Roughly 54k reads and 54k writes,
about **$0.13** at current Firestore pricing. It is idempotent and only ever


## 7. DEPLOYED — 2026-09-06

Authorised by the owner: "Application is in production and it's live.
Everything should be backward compatible." All of the below is live.

### Backward-compatibility decisions made during the deploy

Three things were changed from the plan *because* the app is live. Each one
would have broken something.

1. **`/users` read is split, not simply closed.** `users/.read` is now
   `auth != null`, which blocks anonymous enumeration of all 81,431 records.
   But `users/$userId/.read` stays `true`, because the Next.js site at
   `RunningWebsites/MM2WEB` reads `users/{uid}` through `getUserProfile()` and
   may do so before sign-in. Closing the whole subtree would have broken the
   website and every old app build. Verified after deploy: the bulk dump
   returns `Permission denied`, a single profile still reads.

2. **A `.validate` rule in the repo was dropped, not deployed.** The repo copy
   of `database.rules.json` carried a validation on
   `private_messages/$chatKey/messages/$msgId` enforcing chatOffTrade /
   chatOffGeneral. Production did **not** have it: the repo file had drifted
   ahead of live. Deploying it would have newly gated every private message on
   string surgery over `$chatKey`, failing closed if wrong. That node now
   matches production exactly.

3. **The rules gained the app's founder-email bootstrap.** The write rule
   requires an admin, and **no account in this project has `users/{uid}/admin`
   set** — none of the three founder emails has even signed in. The admin UI
   would have appeared and every role grant would have been denied. The rule
   now accepts the same three verified emails `Code/GlobelStats.js` already
   trusts, so the first sign-in can grant the real flag.

## 9. Polls — 2026-09-06

Created by staff in the Admin Dashboard, shown in the feed. Same shape as
Adopt Me's.

### What already existed

`Code/Engagement/PollCard.jsx` — 218 lines, complete, with voting,
vote-changing and animated result bars. It had **never been imported by
anything**, and there was no way to create a poll. Dead code with no producer
and no consumer.

So the work was not writing a poll feature; it was building the two ends.

### Storage

`polls/{id}` in Firestore. The shape is dictated by `PollCard`, which reads
and writes it directly:

```
question    "Which is worth more?"
options     [{ text, votes }, …]
totalVotes  number
voters      { uid: optionIndex }     ← one entry per voter, so a re-vote moves
active      boolean                     the count instead of adding to it
createdAt   Timestamp
createdBy   uid
```

`active` is new. It is the admin's on/off switch and the field the feed
filters on, so retiring a poll hides it everywhere without destroying votes.

### Admin side

A **Polls** tab in the dashboard, open to moderators as well as admins:

- Question plus two to six options. Six is not arbitrary — `PollCard` has a
  six-colour palette, and a seventh bar would reuse a colour and read as a
  duplicate option.
- Rejects a blank question, fewer than two options, and duplicate options.
- Three active polls at a time. More just pushes real posts off screen.
- Each row shows live result bars, so you can read the outcome without
  leaving the dashboard.
- Hide/show toggles `active`. Delete removes the poll and warns how many votes
  go with it.

### Feed side

`DesignMainScreen` opens a live listener on the three newest active polls and
puts them at the top of the list.

A listener rather than a one-shot read, so a vote cast on another device or a
poll an admin just published appears without a pull-to-refresh.

They ride **in the list data**, not in `ListHeaderComponent`. That header is
`stickyHeaderIndices={[0]}`, so a poll placed there would pin itself over the
feed permanently instead of scrolling away.

A listener error, most likely a missing index, is caught and the strip simply
does not render. A broken poll query must not take the feed down with it.

### Index

`polls (active ASC, createdAt DESC)` added to `firestore.indexes.json` and
deployed. Verified live: the exact query the feed issues is accepted and
returns without error.

### Known limitation

Firestore rules are still stage 1 — public read, authenticated write — so a
determined signed-in user could write directly to a poll document and alter
the tally. Voting is not tamper-proof. Closing that needs a per-collection
rule that only permits a vote-shaped update, which belongs with the wider
stage-2 rules work rather than being bolted on here.
